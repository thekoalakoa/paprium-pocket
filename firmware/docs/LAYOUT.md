# Memory layout of the cart MCU firmware

Two layouts build from the same sources (`fwbuild.json` "layouts"). Stage 0, 1, 3 and 5 below are steps of the 0.3.0
work (README.md, "Terms"); the s1 images are the new firmware that `tools/fwbuild.py s1` builds. The cart MCU is the
NEORV32 soft CPU in the core; IROM is its code memory, WRAM its working RAM, and the RTL the core's hardware
description.

| | `legacy54k` (0.2.6) | `pocket72k` (0.3.0, locked 2026-10-10) |
|---|---|---|
| IROM | 54 KB: rom0 32 KB + 22 KB extension (11:1 slice mux) | **72 KB: rom0 32 KB + one 40 KB extension, 2:1 select** |
| brain | 0x5360-0xD2EB | 0x5360-0xD2EB, same bytes |
| firmware room in the IROM | 21,344 B below the brain + 1,300 B tail | **21,344 B below the brain + 19,732 B above it = 41,076 B** |
| WRAM | 32 KB (aliased over 256 KB) | **48 KB, the 0.3.0 map** |
| linker script | `board/pocket/link/legacy54k.ld` (the script the shipped 0.2.6 build generated; since then only its comments and its ASSERT message texts changed) | `board/pocket/link/pocket72k.ld`, generated by `tools/mkld.py` from `pocket72k.json` |
| runs on | the 0.2.6 RTL (EXT_KB = 22, WRAM 32 KB) | **the stage-1 RTL only** (the first new-core RTL: EXT_KB = 40, WRAM 48 KB). Never load a pocket72k image into a 0.2.6 bitstream: its stack top 0x8000BFFC aliases into the locked code window there, and its .rodata and .data image run past the end of the 22 KB extension (0xD7FF). |

`board/pocket/link/pocket72k.json` is the source of truth for the new layout. `tools/mkld.py`, `tools/fwsize.py`,
`board/pocket/include/pocket_map.h` and this page follow it; `tests/check_tree.py` fails if the header or the
committed `.ld` drift from it. All addresses are MCU bus addresses; ranges are inclusive below.

## IROM, pocket72k (0x00000000-0x00011FFF)

| range | bytes | region | holds |
|---|---|---|---|
| 0x0000-0x535F | 21,344 | `irom_lo` | crt0 (`.text.boot` must sit at 0: the reset vector), then `.text`: every firmware function not listed for `irom_hi` |
| 0x5360-0xD2EB | 32,652 | `brain` | the CPU MATE brain (`brain.bin`, linked for 0x5360: jump table, text, its rodata). Fixed bytes. |
| 0xD2EC-0x11FFF | 19,732 | `irom_hi` | `.text_hi` (input sections listed in `irom_hi_text`), `.rodata`, and the `.data` load image |

- **Image files:** `mcu.txt` = rom0 (8,192 words, 512 lines), `mcu_ext.txt` = 0x8000-0x11FFF (10,240 words, 640
  lines); both in the 0.2.6 format (16 words a line, upper-case hex, CRLF, one trailing space). 0x12000-0x1FFFF is not
  backed. The 17-bit port reaches 0x11FFF, but the 0.2.6 `mcu_irom` module misreads its extension at EXT_KB = 40: the
  RTL of stage 1 selects it by `addr[16] | addr[15]` (docs/MCU_INTERFACE.md, finding 1; docs/STAGE1_PLAN.md, row M4).
- **Fetch and load cost are the same in both halves** (rom0 and extension both read in one clock; measured on a
  simulation of the RTL with our cycle bench: fetch 4, load 10). So the lo/hi split is about room, not speed:
put code wherever it fits.
- **Why rodata and the data image go above the brain:** they leave the 21 KB below the brain to code, which is what
  grows. The four functions 0.2.6 already placed after the brain (`ppm_reset`, `ppm_init_cmd_ptr`,
  `ppm_chip_preload`, `mdp_init`) stay there.
- **When `.text` outgrows `irom_lo`** the link fails with "region `irom_lo' overflowed". Move whole input sections
  (cold or boot-time functions first) into `irom_hi_text` in the JSON, regenerate the `.ld`, rebuild.

## WRAM, pocket72k (0x80000000-0x8000BFFF, 48 KB)

| range | bytes | region | holds | crt0 |
|---|---|---|---|---|
| 0x0000-0x181F | 6,176 | `wram_data` | `.data`, `.bss` (hot firmware data), then the buddy glue's `.noinit` | `.data` loaded from its image in `irom_hi`; `.bss` cleared; `.noinit` left alone (the glue clears it at its first event) |
| 0x1820-0x2ABF | 4,768 | `brain_data` | the brain's data, fixed by its link: cap 1 KB, CM 0x1C20, T16 0x2020, key / CM_BAD / counters, movem shadow, brain RAM 2 KB at 0x22C0 | not touched |
| 0x2AC0-0x2BFF | 320 | `wram_sched` | `.bss_noclear`: the five 0.2.6 objects whose start value is never read (lists, `ppmio`, two debug rings). In 0.3.0 the scheduler state and timer wheel; the s1 images keep them in `wram_data` (see "The s1 images") | **not cleared** |
| 0x2C00-0x6BFF | 16,384 | `wcode` | the write-locked code window, loaded with the bitstream (`wram_hi/lo.txt`): `cf.bin` at 0x2C00, 64 zero bytes, image tables 0x4110-0x4647, then the glue's code and rodata | not touched |
| 0x6C00-0xABFF | 16,384 | `wram_upper` | 0.3.0 upper data: synth state, scaling buffers, extra .bss, WRAM-ROM spill, and the boot overlay at power-on. In the s1 images: `.bss_upper` (input sections `.bss_upper.*`) at its start: F5's 4 KB buffer and the CPU MATE glue's state; in TEST also the register-write oracle log (2 KB), the audio-call log (1 KB) and the counters | the s1 crt0 clears `.bss_upper` a word at a time (the linker script asserts its alignment); the 0.2.6 crt0 never touches the region |
| 0xAC00-0xBFFF | 5,120 | `stack` | the stack, `__crt0_stack_begin` = 0x8000BFFC. 0.2.6's static bound with F5's 4 KB buffer is 4,960 B; the lockstep run's deepest point is 4,208 B (measured). The s1 images: static bound 2,580 B TEST / 1,668 B RELEASE (scheme s1, the check that fails their build; only the song tick of stage 5 is still a stand-in) | the s1 TEST crt0 fills it with 0x5AC3A55A (high-water mark) |

- **Images:** `wram_hi.txt` / `wram_lo.txt` = the even / odd bytes, 24,576 lines each (0.2.6: 16,384), zero outside the
  bitstream-initialised ranges (today only the code window; later the WRAM-ROM spill and the boot overlay).
  The newer RTL (test build 4's MCU fast path: the WRAM tightly coupled to the NEORV32 as four 8-bit lanes) reads
  `wram_b0.txt` .. `wram_b3.txt` instead: the same bytes, line k of `wram_b<i>` = byte 4k + i, 12,288 lines each.
  `tools/mkimage.py` writes both forms from one byte array (`tests/check_images.py` checks they hold the same bytes).
- **What the stage-1 RTL must provide for this layout:** EXT_KB = 40; WRAM 48 KB decoded so that
  0x80000000-0x8000BFFF is real memory (with the bank select registered, a lesson from an earlier FPGA fit); the
  store-lock map extended to 48
  bits (the window stays KB 11-26 locked).

## What never moves (and how it is checked)

| fixed part | where | check |
|---|---|---|
| brain bytes | IROM 0x5360-0xD2EB | `.brain_irom` placed at 0x5360 and ASSERTed to end at exactly 0xD2EC; `tests/check_images.py` compares the image bytes with `brain.bin` (md5 1b64e14d) |
| `cf.bin`, pad, image tables | WRAM 0x80002C00, 0x800040D0, 0x80004110-0x80004647 | `.wram_text` ASSERTed at 0x80002C00; image bytes compared with `cf.bin` / `rodata.bin` and with the legacy build |
| brain data | WRAM 0x80001820-0x80002ABF | no output section may use it (`__noinit_end <= 0x80001820` ASSERT; the region is outside every MEMORY range) |
| firmware data addresses | WRAM 0x80000000-0x8000181F, 0x80002AC0-0x80002BFF | pocket72k keeps every data symbol at its 0.2.6 address (measured: 110 TEST / 70 RELEASE symbols, all equal) |

The brain files live outside this tree; `fwbuild.py` refuses to build if their md5s differ (`fwbuild.json` "brain").

## Measured sizes: the final 0.2.6 modules in both layouts (milestone 2)

From `build/pocket/<layout>/<variant>/layout.txt` (`tools/fwsize.py`, ELF section headers).

**What the relink changed (measured, legacy54k vs pocket72k, same variant):** the 21 object files are identical (the
compile does not depend on the layout); every function keeps its 0.2.6 address and size (`.text` from 0, `.text_hi` =
the old `.ext_text` at 0xD2EC); every data symbol keeps its address; the code window (`cf.bin`, tables, glue) is
byte-identical (`wcode.bin` 29189a78 TEST / 2c1ce124 RELEASE). Only four things move: `.rodata` (to `irom_hi`), the
`.data` load image (crt0's copy source), `__crt0_stack_begin` (0x8003FFFC -> 0x8000BFFC) and `__stack_floor`. So the
instructions that differ are exactly the address constants that point at them: RELEASE 9 instructions in 3 functions
(crt0 x 2, `__clzsi2`), TEST 63 in 14 (the same plus the printf strings and tables of the debug build).

**Reading it (estimated, against the 0.3.0 design):**
- The 72 KB layout gives 18,432 B more firmware room than 0.2.6 (41,076 vs 22,644 B incl. the 1,300 B tail); 8,192 B
  of that is the step from 64 to 72 KB (a 64 KB build would end `irom_hi` at 0xFFFF: 11,540 B).
- Whether 0.3.0 fits is in `docs/BUDGET.md` section 4 (estimated; the song engine measured as a draft): the resident
  code (IROM + code window + WRAM-ROM, room 54,072 B net of the data in `wram_upper`) fits on the central forecast
  with about 2.4 KB (TEST) / 5.2 KB (RELEASE) to spare, once about 10.6 / 7.8 KB of it sits in the code window and
  WRAM-ROM; the worst case is 11-16 KB over. (Superseded 2026-10-10: this page first quoted the 0.3.0 design's
  32.3 / 38.6 / 45.8 KB with table-driven gates and said the central case fits in the IROM alone and the hi case needs
  the planned spill. The measurements of stage 0 showed otherwise: the central case needs the spill, the hi case does
  not fit even with it, and a gate table saves about 0.5 KB, not ~3 KB.)
- The TEST build is 4,420 B bigger than RELEASE here (debug aids), and both fit with room to spare, so one 72 KB fit
  serves both (the locked decision's reason).
- **WRAM is the tight one at stage 0:** `wram_data` is full in TEST (0 B). New 0.3.0 data goes to `wram_upper`
  (16 KB free). (Separately, the TEST build's debug region in battery RAM moves off 0x900 with the saves decision.)

## The s1 images (measured 2026-10-11, work item W11 of docs/STAGE1_PLAN.md)

`tools/fwbuild.py s1` links the s1 source set (`fwbuild.json` "s1") into the same pocket72k layout and linker
script. From `build/s1/pocket72k/<variant>/layout.txt`, with work items W3-W10 linked:

| region | size | TEST used / free | RELEASE used / free |
|---|---|---|---|
| irom_lo (`.text`) | 21,344 | 18,628 / **2,716** | 15,516 / **5,828** |
| irom_hi (`.text_hi`, `.rodata`, the `.data` image) | 19,732 | 17,640 / **2,092** | 14,404 / **5,328** |
| **firmware IROM total** | 41,076 | 36,268 / **4,808** | 29,920 / **11,156** |
| wram_data (`.data`, `.bss`, `.noinit`) | 6,176 | 5,664 / 512 | 5,376 / 800 |
| wram_sched (`.bss_noclear`) | 320 | 288 / 32 | 256 / 64 |
| wcode (`cf.bin`, tables, the glue) | 16,384 | 9,380 / 7,004 | 8,800 / 7,584 |
| wram_upper (`.bss_upper`) | 16,384 | 7,600 / 8,784 | 4,200 / 12,184 |
| stack (static bound, scheme s1) | 5,120 | 2,580 / 2,540 | 1,668 / 3,452 |

- **The irom_lo / irom_hi split (reviewed in W11: nothing moved).** `irom_hi_text` in `pocket72k.json` sends whole s1
  objects above the brain: app init, the boot page, the re-hosted 0.2.6 bodies, the VU rows, the F5 copy, `disp.c`,
  `jobs.c`, the watchdog, the fatal halt, the MCU reset, the TEST counters and debug save, and the interim audio.
  crt0, the trap entry, the scheduler, the wheel, the status layer, the event post, the register accessor and the
  moved 0.2.6 files stay in irom_lo. No 0.2.6 object has those names, so the milestone images do not move. Both halves
  fetch at the same cost, so the split is about room only; both keep at least 2 KB free in TEST. If one overflows, the
  link fails ("region `irom_lo' overflowed"): move another whole object in the JSON and regenerate the `.ld`.
- **The code window's s1 objects (2026-10-19).** `wcode_text` in `pocket72k.json` places whole s1
  objects in `.wram_text` after the glue (`tools/mkld.py`; no 0.2.6 object has these names, so the milestone images do
  not move; the window's fixed bytes, `cf.bin`, the pad and the tables, stay first). Our code for the chip's SFX channels
  (`interim/s1/sfx_s1.c`: 4,552 B TEST / 4,440 B RELEASE, the cold parts compiled for size) went there because the
  TEST IROM had 212 + 168 B left; its one clock figure is read in `audio_s1.c` (`s1_sfx_blk3`), as the window must
  not differ between the two clocks (`tests/check_clock.py --images`); `f5_s1.c` moved from irom_hi to irom_lo to
  even the two halves. Measured (TEST / RELEASE): irom_lo 916 / 4,328 B free, irom_hi 936 / 5,412, wcode 2,420 /
  3,112, wram_data 464 / 784, wram_upper 7,852 / 11,576.
- **Test build 4a, 2026-10-21 (stage 5): the TEST image's sound-cache probe in the code window.**
  `board/pocket/s1_cache4a.c` (boot only, the 68000 held: 1,420 B, compiled for size) follows `sfx_s1.c` in
  `wcode_text`: its first link in irom_lo overflowed it by 412 B (TEST irom_lo had 632 B free and crt0's FEAT check
  needs 40 more). Its debug-save block (324 B) is in wram_upper, which also gains 512 B from the audio-call log's 128
  calls. RELEASE has no such object, so its images do not move (byte for byte test build 4's). Measured TEST: irom_lo
  572 B free, irom_hi 912, wcode 940, wram_upper 7,928.
- **Test build 4b, 2026-10-22 (stage 5): the WRAM boot overlay.** The first-boot unpack (`board/pocket/boot/c4b_ovl.c` +
  `core/wavpack`, -Os) is linked on its own (`board/pocket/link/c4b_ovl.ld`) and placed by `tools/mkimage.py
  --wram-blob` at 0x80006C00 in the WRAM image (a second bitstream-initialised range, 0x80006C00-0x8000ABFF): 15,124 of
  16,384 B (`build/s1/pocket72k/<v>/ovl/ovl.txt`; identical in TEST and RELEASE). It runs from crt0 before .data / .bss
  (68000 held), then crt0's `.bss_upper` clear overwrites it. Its scratch is crt0-made memory too: 3,680 B at the start
  of wram_data (must end at or below `__BSS_END__`: the build checks it) and 3,528 B (the decoder's context and sample
  buffer) at the stack floor 0x8000AC00 (it runs on crt0's stack from the top, measured 572 B deep; the build keeps
  1,536 B clear). The IROM stub (`boot/boot_cache.c`, 348 B) is in irom_lo in both images; the TEST record writer
  (`s1_cache4b.c`, 468 B) takes test build 4a's sound-cache probe's place in wcode_text. Measured TEST: irom_lo 212 B
  free, irom_hi 912, wcode 1,892, wram_data 416 (.noinit + 64: the record), wram_upper 7,928 after the boot; RELEASE:
  irom_lo 4,048.
- **Scheduler state (W11: kept where it fits).** The scheduler and wheel state is 136 B of `.bss` in wram_data
  (`sched.c` 112, `wheel.c` 24). wram_sched has 32 B (TEST) / 64 B (RELEASE) left after the four not-cleared 0.2.6
  objects of `mame.c` (two lists, two debug rings; 0.2.6's `ppmio` is not linked in the s1 images). So the state does not
  fit there, and crt0 does not clear that region either. It stays in wram_data, which keeps 512 / 800 B free.
- **wram_upper** holds F5's static 4 KB buffer (4,096), the glue's state (104), and in TEST the oracle log (2,052), the
  audio-call log (1,028) and the counters (320): 7,600 B TEST, 4,200 B RELEASE. (From 2026-10-21, test build 4a: the
  audio-call log 516 B and the cache probe's block 324 B in TEST.)
- **What is checked:** `tests/check_images.py s1` (brain bytes, code window, crt0 at 0, trap entry in irom_lo, no
  0.2.6 start-up, no weak hook default linked in test / release); the stack and size checks run on every s1
  build (`docs/BUDGET.md` section 7).

## Off-chip memories (no firmware section uses them yet)

Unchanged from the 0.3.0 design: SRAM 0x18000-0x1FFFF for the cold pack
and MegaWire (run in place), the buddy's PRG window 0x10000-0x12001 and Word RAM mirror 0x20000-0x3FFFF; CRAM (the
Pocket's cellular RAM) die 0 for the wave-bank cache, SFX bank and DT echo; SDRAM exactly 0.2.6's workspace. With MCU
interface v1.2 (proposed): the RTL sprite decoder is a second client of SDRAM port 2 (beside the MCU) and writes the decoded
blocks and DA streams where 0.2.6's MCU unpacked them (the scratch at `0x1E0000`, a DA's destination), so the
workspace layout does not change. The linker script gets SRAM output sections when the cold pack exists (stage 3).
