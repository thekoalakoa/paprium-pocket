# core/mw - the cart's MegaWire code (stage 3, test build S3b)

Copyright (C) 2026 Marsupial Solutions LLC. SPDX-License-Identifier: GPL-3.0-or-later.

The cart chip (the STM32 microcontroller on the real cartridge) drives a MegaWire module (an ESP8266 on a cable) when
one is plugged in. With nothing plugged in it still runs its MegaWire task about ten times a second: the presence
probe, the status word ($1FE6 bits 0-2 = 0, so the game shows "MODEM : NONE" and no MEGAWIRE row), and the
information block at $1B20. This directory does what the cart does, at the cart chip's addresses (cited in every
function), on a Pocket that has no module socket. It was written by our team from our own study of how the cart
behaves, and is built with FW_MW (board/board.h).

| file | where it runs | what |
|---|---|---|
| `mw.h` | - | the cart chip's RAM blocks at their sizes, the interface, what is done and what is not built yet |
| `mw_boot.c` | IROM | the thread's first work after the 68000's release: the SRAM image's check; the cart's MegaWire code runs if it passed (the MegaWire option bits are never read) |
| `mw_res.c` | IROM | the init's interrupts-off block (the cart chip's cpsid / cpsie in 0x080218FC) and the E7 / A9 / A6 bodies, resident |
| `mw_task.c` | SRAM image | the init 0x080218FC, the TIM7 task 0x080219CC (incl. the E7 packet 0x08021388), the information block 0x08021728 |
| `mw_drv.c` | SRAM image | the module driver's presence probe and link-up 0x0801E824 (no module: the probe reads 0) |
| `mw_screen.c` | SRAM image (cold) | the A858 screen: the screen loop 0x080225F8, the page loader 0x08022404, the lines 0x080224B4, the 68000 held and started on page A |
| `mw_text.c` | SRAM image (cold) | the cart program's text, unpacked from the player's ROM into CRAM (docs/MCU_INTERFACE.md 3.8, MWTEXT) when the screen first needs it, by the firmware's shared 0x81 decoder (core/song/unpack81.c, its checked entry, in IROM) |
| `mw_page_a.c` | SRAM image (cold) | page A: our 68000 program for the screen (generated by tools/mkpagea.py) |
| `mw_int.h` | - | the internal calls |

Words used on this page. IROM is the MCU's code memory inside the FPGA (the MCU is the processor this firmware runs
on), WRAM its working RAM. The Pocket SRAM is a RAM chip on the Pocket that our core maps into the MCU's address
space, and CRAM is the Pocket's cellular RAM, another such chip. RAMDP is the cart RAM that both the 68000 and the MCU
see. L3 is the thread, the lowest priority level of the scheduler (core/sched). TIM7 is the cart chip's timer that
runs its MegaWire task. Row numbers such as B49 are rows of docs/ALLOWLIST.md, the list of our known differences from
the cart chip.

- The code runs in place from the Pocket SRAM (the SRAM image, built with the firmware and carried in the
  Little-Man Firmware file, which the core's boot stub copies into SRAM; docs/MCU_INTERFACE.md section 3.7), in the
  thread (L3), below every reply path. Its RAM is at SRAM 0x18C00.
- The gates of the MegaWire posts (A4, A6, A8, A9, AA58, E7) are resident: `core/dispatch/disp.c`.
- The Pocket menu of 0.3.0 has no MegaWire row (B Jam's decision of 2026-11-01), and this firmware never reads the
  MegaWire bits of the option word (bits 16-18, docs/MCU_INTERFACE.md section 5). With no module the game shows
  "MODEM : NONE", as on a cart. A missing or refused SRAM image leaves the MegaWire status at 0 (no module), as in
  test build 5 with the option Off.
- The A858 screen needs no module: the game's Options pad code posts A858 with nothing plugged in, and the cart then
  shows its MegaWire screen. Ours does what the cart chip does (the screen loop, the pages, the hold, the lines) with
  page A written by our team from the real screen's behaviour and page B the ROM's own font, both read or built at run
  time; checked against the cart chip by `tests/equiv/mw_screen.py` and on a modelled VDP by `tests/equiv/mw_pagea.py`.
- Not built yet: the paths that need a module (the AT stack, the server, the MegaWire menu's states, the record's save,
  the updater), and the cart's network text in the no-module paths that write it (row B49).
- The MegaWire server's name is ours, www.koalakoa.com, where the cart names its own (row B51).
- The image has a hot part (the task) and a cold part (the screen, the text, page A), each with its own CRC-32. The
  thread checks both first after the 68000's release, so the 68000 starts at the same time as in test build 5, which had
  no MegaWire code (a check before the release moved the game's frames against the video chip's); a cold part that
  fails its check leaves the task running and the screen uncalled (docs/MCU_INTERFACE.md section 3.7).
- Checked against the cart chip, run in our model of the cart: `tests/equiv/mw_oracle.py` with the host
  harness `tests/s1/mw_host.c` (fwbuild's s1 program `mw_host`): every cart RAM word and $1FE6 store of ~4,070 ticks
  and the posts among them (the A4 posts, the attract mode's A9 + E7 pairs and their 46 s give-ups, an E7 inside
  state 3, A6, the error packets, game packets of 1-251 bytes, a stale request tail, the MegaWire menu's 0x82 / 0x84
  packets to their give-ups), the RAM blocks byte for byte; its planted
  bugs MW_BUG 1-3 must be caught, and so must two plants at the edges of the row B49 mask (the network text's mask
  follows the cart chip's own request length). On the RV32 board
  model, `tests/equiv/mwboot.py` runs the SRAM image itself: the image check's 13 cases after the 68000's release, the
  lock, the port from SRAM, the game's C6 count, On = Off, the $1B20 block and the post gates against the cart chip's,
  and the A858 screen's hold and release at the cart chip's own waits (+74.0 / +374.0 ms after the post, within 2 ms).
- The task runs once per TIM7 period, as on the cart: a tick the thread cannot take in time (a long job such as C6's
  set-up) runs late, never dropped (`mw_due` / `mw_ran`). The thread runs it one of the cart chip's own steps at a
  time (the request and the task state's step, the driver step, the status word, the information block's bytes, its
  RAMDP stores 18 words a step, the tail), in the cart chip's order, and starts none while the game's sprite frame is
  open (from its AE to its AF, for up to 33.4 ms after the thread first saw it open) or a 68000 post waits in mailbox
  B: the check is made with the interrupts off and the step is entered with them still off; it opens them first and
  leaves at once if an AE was taken then. An AE that comes while a step runs lets that one step end (the thread cannot
  stop the cart's code inside a step), and the next step waits for the frame's AF or the 33.4 ms. A frame open longer
  than that no longer holds the task, which then runs its steps between the game's posts: the game keeps some frames
  open for many frames, and the Options pad code's A858 jumps to cart RAM before its AF.
